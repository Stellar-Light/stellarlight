## How an approval is applied

Nothing in this file touched the database. The owner marks slugs approved; a
curator adds each to `STATUS_FIX` in `scripts/data/curation-maps.ts`:

```ts
"<slug>": {
	from: "Live",
	to: "Live",
	basis: "human-verified",
	asOf: "<date the owner read the packet>",
	sourceUrl: "<site URL from the packet>",
	note: "<packet reason, short and dated>",
},
```

This works today — verified against the curate loop ("Status fixes
(from-guarded)" in `scripts/data/curate-projects.ts`): the only skip is
`d.status !== fix.from`, so a `Live → Live` entry passes and writes
`statusBasis`, `statusAsOf` and `statusSourceUrl` alongside a no-op status.
It is the existing pattern — the 2026-08-28 sourced-queue pass stamped benji,
friendbot, warmancer, wisdomtree, stellar-laboratory, hana and liquify exactly
this way ("from==to entries move nothing; they fix the evidence").

Things to know before adding rows:

- `note` lands in `lifecycle.note` only when the row has none, and agents
  quote it verbatim — keep it one factual, dated sentence.
- A human-verified Live entry with a `sourceUrl` is re-scanned for pre-launch
  markers at apply time and WARNS on a hit (never refuses) — the human owns
  the contradiction, so read a `leave` row that mentions testnet / waitlist /
  coming soon before promoting it.
- Being in `STATUS_FIX` makes the slug own `status` (`curatedFieldsFor`), so
  the nightly lumenloop sync can no longer write the seed label back.
- `from === to` rows never retire; they re-apply idempotently on every run.
- An `inactive` approval is a `from: "Live", to: "Inactive"` entry with the
  packet's evidence as the note — a status move, so it gets its own dry run.
- Apply via `.github/workflows/curate-projects.yml` (dry-run first, then
  `execute`), then read the row back off `/api/projects`.
- Optional receipt: `pnpm exec tsx scripts/data/capture-receipt.ts <slug> <url> [marker...]`
  writes `improvements/receipts/<slug>-<date>.json` so "verified on <date>"
  is re-checkable later.

Proposals are one word each and the human decides. `verify` = site 200 on the
row's own link, the page names the product, no pre-launch phrase, AND a dated
artifact within 365d that the reason names: a store listing's release/update
date, a dated post on the operator's own blog / changelog / news / feed, a
GitHub release on the linked repo, a push on the linked repo for library-typed
rows only (the source moving is the product), or a developers.stellar.org page
updated within 180d that lists the product as a current provider or tool.
`inactive` = what was seen says the product is gone: the domain does not
resolve, the page is a parking page or a 404/410, or the row's own site now
serves an unrelated business and the linked code stopped years ago. A 5xx, a
timeout, a TLS error or a bot wall is never a verdict. `leave` = everything
else — the page answered but nothing is dated within 365d, the page does not
name the product (a bare hostname, a scaffold title, a client-rendered shell),
a pivot or rename that needs a relink rather than a stamp, or the check could
not run. A repo push alone never makes a non-library row `verify`: on
2026-09-05 two Live verdicts built on a banner plus a push were overturned
within the hour. Rows marked `[hand-read; rule said X]` were re-read against
the page and the mechanical rule was overridden for the reason given.
