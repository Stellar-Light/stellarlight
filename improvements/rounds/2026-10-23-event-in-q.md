# 2026-10-23: an event named in q becomes the hackathon filter

## Scope

searchHackathonBuilds treats an event name in q as words to match against
submission text. `GET /api/hackathons/builds?q=HackMeridian%202025&limit=20`
served 5 builds on live 1.9.95 (2026-10-23T14:23Z), none of them from
hackmeridian-2025, while `?hackathon=hackmeridian-2025` served that event's
six winners (curated rows with no repo text, so their own text never
matches). Agents put event names in q ("HackMeridian 2025 winners", "builds
from Stellar Hacks: Blend"), and the v1 benchmark questions q08, q11 and q12
ask builds search for the HackMeridian 2025 winners this way and get
nothing. This round makes builds search apply an event named in full in q
as the filter, warn on a partial or ambiguous name, and say what it
inferred. Builds search only: analyze, vetIdea and compare are unchanged.

## Design (fixed before any capture or replay)

- Event list: every event the cached builds index holds (each row's
  `hackathon`) plus the curated events off DoraHacks
  (`src/data/curated-hackathons.ts`, which holds hackmeridian-2026, an event
  with no stored submissions). No database or network read is added.
- Matching: q and every name are compared accent-free, lowercased, as runs
  of letters and digits, so every other character (":", "|", the dashes,
  ",", "+", "&") separates words, on whole words. A title matches when its
  words occur in q as one run. A slug matches when q holds it as typed, with
  its hyphens: `build-on-stellar` and `stellar-latam` are slugs made of
  common words, and with hyphens ignored they would match "build on
  Stellar" and "Stellar LATAM" in topic queries. The longest match wins over
  any shorter one it overlaps.
- Inference: only when the request has no `hackathon` parameter and every
  kept match names one and the same event. That event is applied as the
  filter and the matched phrase is removed from q. The rest is searched as
  usual inside the event; when it holds no word other than stopwords and
  words that ask for the event's own entries (winners, builds, projects,
  submissions, hackathon and their forms), nothing is left and the request
  is served as a filter-only request is today (winners first).
- Partial or ambiguous: with no full match, a run of q's words that starts
  the titles of two or more events and holds a word that is not a stopword
  ("HackMeridian", "Stellar Hacks"; not "Stellar" or "Build on Stellar")
  infers nothing and adds one `meta.warnings` line naming the candidate
  slugs and saying to pass `hackathon=`. Full names of two different events
  also infer nothing and get the same kind of line.
- Explicit filter: any `hackathon` parameter, even empty, turns inference
  off. A non-empty one that selects other events than the one q names adds a
  warning. `hackathon=` with no value is the documented opt-out: q's words
  are searched as text in every event, as today.
- Reporting: `meta.inferredFilter: {hackathon, matched}` and one warning
  naming the opt-out.

Probes 16 to 21 are this lane's own, aimed at false positives: event names
made of common words (16, 17, 21), event words inside a name (18, 20) and a
project named with an event word (19, 20).

Decision on probe 10: "ZK Gaming" is the end of one event's title
("Stellar Hacks: ZK Gaming"). The whole-name rule infers nothing, and the
partial warning does not fire either, because it reads only the start of
titles shared by two or more events. A middle-of-title run unique to one
event is as often a topic as a name: under the same rule "real world" (from
"Stellar Hacks: Real-World ZK") would warn on every real-world-asset query
(probe 18). The event's own builds already match "zk gaming" by their own
words.
